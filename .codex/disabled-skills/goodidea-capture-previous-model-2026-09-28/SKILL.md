# Good Idea 捕捉

保护一个正在形成的认识。忠实保留用户的实际表达，只恢复理解这次连接如何形成所必需的上下文。不要判断它是否具有长期价值，也不要主动把讨论推向制卡。

## 不可破坏的边界

- 用户拥有议题、含义以及是否正式沉淀的决定权。
- 严格区分原始对话、候选表达和经用户确认的正式闪念卡片。
- 不得用摘要改写或替代原始对话。
- 外部来源只是来源，不代表用户的立场。
- 模型的理解在用户确认前只是假设。
- 不能因为讨论已经清楚，就自动创建正式闪念卡片。
- 一次捕捉只有原始思考记录、最终产生零张闪念，也是合法结果。
- 不判断这个想法是否值得长期投入；这属于后续认识发展流程。

## 能力边界

本 Skill 可以在发送实质回应前，先保存每条已经收到的消息。它不能保证消息在模型开始推理前已经落盘，不能拦截当前调用之外的消息，不能保证在工具运行前发生宿主崩溃时仍不丢失，也不能独自完成定时软关闭或多个并发对话的协调。不得声称已经提供这些运行时保证。

以当前 Good Idea 项目作为存储边界，预期存在：

```text
数据/记录/闪念/原始思考记录/
数据/记录/闪念/
数据/模板/original-thought.md
数据/模板/flash.md
```

如果这些路径不存在，继续在当前对话中保护用户表达，明确说明当前无法进行可靠的本地落盘，不得自行选择其他存储位置。

## 进入捕捉模式

只有用户明确开始一次捕捉，或清楚要求记录一个正在形成的想法时，才进入本模式。不能仅凭普通聊天内容自动推断用户已经进入捕捉。

进入时：

1. 在 `数据/记录/闪念/原始思考记录/` 中，为本次捕捉创建一份原始思考 Markdown 文件。
2. 文件名使用 `YYYY-MM-DD-简短标题.md`。从用户自己的表达中提取最短且不失真的标题；尚无有效标题时使用 `YYYY-MM-DD-未命名思考.md`。只有发生同名冲突时才增加 `-2`、`-3` 等后缀。
3. 采用 `数据/模板/original-thought.md` 的文件形状，但不能依赖模板链接的规则文件一定存在。
4. 将触发本次捕捉的用户消息原样保存为第一条用户消息。使用当前本地时间；能够确定显示名称时使用显示名称，否则使用 `用户` 和 `Agent`。
5. 即使对话中出现多个可能的认知种子，也只保留这一份原始记录。只有用户后来要求形成闪念候选时，才判断是否拆分。

不得在原始消息块中加入摘要、推断出的意图、标签、状态或用户没有表达的背景。

在当前对话上下文中保留本次创建的文件路径，之后只向这个路径追加。不得根据“最近修改的文件”猜测当前捕捉记录。如果上下文已经无法确定活动记录，应请用户指出原记录或明确开始一次新捕捉，不能自行猜测。

## 保存全部可见对话

捕捉模式下的每一轮都按以下顺序处理：

1. 在进行任何实质回应或上下文搜索前，把当前用户消息原样追加到活动原始思考记录。
2. 起草将要发送给用户的完整可见回应。
3. 在发送前，把这段完全相同的回应和时间追加到原始记录。
4. 如果写入失败，立即说明失败；当前对话中仍保留用户原话，但不得声称已经保存成功。

不要记录隐藏推理或工具输出。轻量状态确认、实质回应、闪念候选、用户纠正和确认都属于可见形成过程，需要保存。

避免重复追加。如果同一条消息可能已经保存，写入前先检查活动记录末尾。

## 保护连续表达

默认用户仍在表达。消息结束不等于用户已经交出话语权。

只有当用户的语义明确要求 Agent 回应、理解、整理、判断或开始处理时，才认为用户交出了当前一轮话语权。这是语义判断，不依赖固定关键词。例如：“我说完了，你怎么看”“你先说说你的理解”“可以开始处理了”。

用户尚未交出话语权时：

- 不理解分析、不总结、不搜索、不提问、不分类、不提出制卡；
- 保存当前消息；
- 只发送不会改变思考方向的简短记录确认，例如“已记录，你继续。等你明确让我回应。”；
- 发送前先把这条确认写入原始记录。

判断不清时，优先继续听。

交出话语权只允许 Agent 开始当前一轮回应，不表示捕捉已经结束，也不授权创建闪念卡片。回应后，重新回到“用户可能继续表达”的默认状态。

## 建立共享理解

用户明确交出话语权后，进入轻量共享理解循环：

1. 用能够暴露解释过程的语言说明当前理解，不把模型理解直接说成事实。
2. 判断是否缺少会实质改变含义的上下文。
3. 选择最小必要动作：直接回应、复述确认、提出一个关键问题，或读取一项高度相关的材料。
4. 让用户确认、补充或纠正。
5. 更新当前理解；用户纠正后，不能继续把旧理解保留为主线。

根据表达体量与清晰度调整介入程度：

| 当前表达 | 介入方式 |
|---|---|
| 小且清楚 | 简短复述或直接回应 |
| 小但模糊 | 只消除一个最影响含义的歧义 |
| 大且清楚 | 收拢形成路径，不额外扩展议题 |
| 大且模糊 | 先询问是原样保护还是继续展开 |

同时满足以下条件时停止继续挖掘：

- Agent 能描述用户这次注意到了什么；
- 能理解哪些对象产生了连接，以及为什么在当前情境中产生连接；
- 必要的触发背景已经保留；
- 不再存在会实质改变含义的关键歧义；
- 用户表达、来源内容和模型推断保持可区分；
- 用户确认当前理解没有实质偏差。

目标是形成足以准确理解并继续生长的共享认识，而不是完成一套完整论证。

## 只在必要时读取上下文

用户仍在表达时不得搜索。用户交出话语权后，也只读取能够消除实质认知缺口的最少上下文。

- 当前表达已经足够时，不读取额外材料。
- 用户模糊引用过去讨论时，在当前项目中定向查找。
- 文件、链接或来源触发了当前想法，并且其内容会影响理解时，只读取直接相关的部分。
- 同一句话存在两种会导向不同认识的解释时，先提出一个关键澄清问题，不进行宽泛搜索。
- 当前理解已经较完整，但不确定是否属于用户时，用自己的话复述并请用户确认。

不能为了安心或追求完整而扫描整个知识库。读取失败时，明确说明缺少什么上下文，并基于已经保存的用户表达继续讨论。

## 由用户控制的出口

### 继续讨论

在当前对话上下文中保持原始思考记录打开，继续保存可见对话。同一次捕捉中的普通分支不新建第二份原始记录。

### 只记录并结束

用户明确表示停止或“先记录到这里”时，追加这条消息和最后的确认，完整保留原始记录，不生成闪念候选，然后结束本次捕捉。

### 形成一张或多张闪念候选

只有用户明确要求把讨论整理或沉淀为闪念时，才能进入候选生成：

1. 根据本次捕捉中已经形成的共享理解，起草一张或多张候选。
2. 在对话中完整展示候选文本，并把它保存到原始思考记录中。
3. 明确标记它是候选；此时不能在 `数据/记录/闪念/` 中创建正式文件。
4. 允许用户确认、修改、合并、拆分、删除或返回讨论。
5. 持续修改，直到用户明确确认具体候选内容。

候选可以表达本次对话中真正共同形成的新理解，但不能隐藏哪些内容来自用户、外部来源或 Agent 推断。

### 保存经确认的正式闪念

用户明确确认候选后：

1. 创建 `数据/记录/闪念/YYYY-MM-DD-标题.md`，只有同名冲突时才增加后缀。
2. 遵循 `数据/模板/flash.md`。
3. 保留 `status: "待辨析"`。
4. 将用户确认的文本写入 `核心内容`；确认后不能再静默润色。
5. 在 `触发情境` 中记录这次想法为什么出现。
6. 原始思考记录确实构成形成依据时，在 `材料与论证锚点` 中链接它。
7. 只有实际使用过外部来源时才链接，并明确它是外部材料，不是用户立场。
8. 在原始思考记录的 `去向` 中链接每一张经确认的正式闪念。
9. 向用户报告实际创建或更新的准确文件路径。

如果用户要求继续一张既有闪念，说明这种可能性，并让用户选择续写、新建、合并或拆分；不能替用户决定。

如果用户另外要求保存外部来源，把它作为一次明确的交接或后续操作。不能把来源正文直接变成闪念，也不能暗示保存来源等于用户接受了其中观点。

## 本 Skill 不实施的内容

使用本 Skill 时，不新增数据库、向量索引、后台监听器、调度器、自动召回管线、48 小时失效机制、状态机或新的对象结构，也不模拟定时软关闭。这些能力需要单独的产品与运行时决定，并由真实使用证据支持。

使用本 Skill 时不要修改产品定义文档。产品定义是设计背景，不是执行无关工作的授权。
