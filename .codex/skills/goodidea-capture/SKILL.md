# Good Idea 捕捉

在不打断、不改写用户思路的前提下，保护原始表达，并逐步恢复理解这次认知连接所必需的上下文。目标是让用户和 Agent 对“用户注意到了什么、为什么此刻产生这条连接”形成共享理解，而不是证明想法正确或追求卡片产量。

## 适用边界

只有用户明确开始捕捉，或清楚要求保存一个正在形成的认识时才进入本 Skill。普通聊天不能自动触发。

以下情况不进入本 Skill：

- 只保存外部资料；
- 登记待办、行动或提醒；
- 审查、辨析或发展一张既有闪念；
- 回答事实问题或执行普通文件操作。

一次明确发起的捕捉对应一份原始思考记录。对话中即使出现分支，也先保存在同一份记录，只有形成闪念候选时才考虑拆分。

## 不可破坏的边界

- 用户拥有议题、含义和是否沉淀的最终解释权。
- 原始对话、闪念候选和正式闪念是三层不同内容，不能互相替代。
- 摘要不得覆盖原始消息，模型推断不得伪装成用户表达。
- 外部来源只用于帮助理解，不自动代表用户立场。
- 只有用户能发起闪念沉淀并认领正式闪念。
- 一次捕捉产生零张、一张或多张闪念都合法。
- 本 Skill 不判断想法是否值得长期投入，也不把闪念发展为永久卡片。

## 明确能力边界

这是 Agent 行为层，不是消息运行时。它可以在收到消息后、发送实质回应前先落盘，但不能保证“消息在模型开始推理前已经保存”，也不能独自提供崩溃恢复、跨对话并发协调或定时软关闭。不得声称这些能力已经实现。

如果可靠性要求超过这一边界，应保留当前对话并明确指出缺失的是宿主消息钩子或轻量运行时，不要用更多提示词冒充程序保证。

## 先保护表达

当前项目的写入位置是：

```text
数据/记录/闪念/原始思考记录/
数据/记录/闪念/
```

文件形状分别见：

```text
数据/模板/original-thought.md
数据/模板/flash.md
```

对象身份和最小内容以 [`../../../规则/内容对象.md`](../../../规则/内容对象.md) 为准。

进入捕捉时：

1. 立即创建 `YYYY-MM-DD-简短标题.md` 原始思考记录；暂无可用标题时使用 `YYYY-MM-DD-未命名思考.md`，只在同名冲突时增加最小数字后缀。
2. 将触发消息作为第一条用户消息原样写入，保留当前本地时间和可见说话人。
3. 在当前对话上下文中记住准确文件路径，之后只向这份记录追加；不得根据最近修改时间猜测活动记录。
4. 如果上下文已无法确定活动记录，请用户指出原记录或明确发起新捕捉，不能自行选择文件。

捕捉期间，每一轮都先把当前用户消息原样追加，再进行搜索或实质回应。起草完整可见回应后，在发送前把完全相同的回应和时间写入记录。轻量确认、候选、修改与确认也属于可见对话；隐藏推理和工具输出不写入。

写入前检查记录末尾，避免同一消息重复追加。写入失败时立即说明，不得声称已经保存成功；读取或解析材料失败也不能改写或丢弃已经收到的用户表达。

## 保护连续表达与话语权

默认用户仍在表达。消息边界不等于交出话语权。

只有用户的语义明确要求 Agent 回应、理解、整理、判断或开始处理时，才认为当前一轮话语权已经交出。这不是关键词匹配。“我说完了，你怎么看”“你先说说你的理解”“可以开始处理了”都可能表示交接。

在用户尚未交出话语权时：

- 不分析、不总结、不搜索、不提问、不分类、不提出制卡；
- 先保存消息；
- 宿主支持状态型确认时只显示轻量状态；否则仅回复不会改变思路方向的最短确认，例如“已记录，继续说。”；
- 将这条可见确认一并保存。

判断不清时继续听。交出话语权只授权本轮回应，不表示会话结束，也不授权生成闪念。回应之后，用户仍可继续补充和纠正。

## 建立共享理解

用户交出话语权后，每一轮只回答三个问题：

1. 当前怎样理解用户注意到的东西和这次连接；
2. 是否缺少会实质改变含义的上下文；
3. 什么最小动作可以消除最关键的不确定性。

最小动作可以是直接回应、复述确认、问一个关键问题，或读取一项高度相关的材料。表达小且清楚时快速回应；小但模糊时只消除一个关键歧义；大且清楚时收拢形成路径；大且模糊时先询问用户希望原样保护还是继续展开。

用户补充或纠正后更新理解，不能继续把旧推断当作主线。模型理解在用户确认前始终是假设。

满足以下条件后停止继续挖掘：

- 能描述用户这次注意到了什么；
- 能说明哪些对象发生连接，以及为什么在当前情境中发生；
- 必要触发背景已经保留；
- 不再存在会改变含义的关键歧义；
- 用户表达、来源内容与模型推断保持可区分；
- 用户确认当前理解没有明显偏差。

目标是“足以准确理解并继续生长”，不是在本 Skill 中完成依据、反例和全部边界的论证。

## 按需读取上下文

用户仍在表达时不读取额外上下文。交出话语权后，也只读取能够消除实质缺口的最少材料：

- 当前表达足够时，不读额外内容；
- 过去讨论的指代不清时，在当前项目中定向查找；
- 文件、链接或来源直接触发想法时，只读与触发点有关的部分；
- 两种解释会导向不同认识时，先问一个关键问题；
- 理解较完整但不确定是否属于用户时，用自己的话复述并请用户确认。

不得为了找全而扫描整个项目。读取失败时，说明缺少什么，并基于已经保存的表达继续讨论。

## 由用户控制出口

### 继续讨论

保持同一份原始思考记录，继续保存后续可见对话。

### 只记录并结束

用户明确表示“先记录到这里”“今天先这样”或同等意思时，保存结束消息和最后确认，不生成候选，然后结束本次捕捉。

### 形成闪念

只有用户明确要求“整理成闪念”“沉淀成卡片”或同等意思时，才执行：

1. 根据当前共享理解生成一张或多张完整候选，并标明“候选”。
2. 在对话中完整展示候选，并保存到原始思考记录；此时不创建正式闪念文件。
3. 允许用户确认、修改、合并、拆分、删除或返回讨论。
4. 只有用户明确认领具体候选后，才按 `数据/模板/flash.md` 创建正式闪念，默认 `status: "待辨析"`。
5. 正式闪念忠实使用用户确认的内容；确认后不得静默润色。保存触发情境，链接真实使用过的原始思考记录与必要来源。
6. 在原始思考记录的 `去向` 中链接所有正式闪念，报告实际文件路径，然后关闭本次捕捉。

如果内容可能是在继续一张既有闪念，只说明这种可能性，让用户选择续写、新建、合并或拆分；不能自动决定。

如果用户另外要求保存外部来源，将其作为明确的后续任务或交接。不能把来源正文直接转成用户的闪念，也不能暗示保存来源等于用户接受其观点。

## 不在本 Skill 中实施

不新增数据库、向量索引、后台监听器、调度器、自动召回管线、48 小时失效机制、复杂状态机或新对象结构，也不模拟定时软关闭。等待真实试运行暴露稳定需求后，再把高频且条件明确的机械动作下沉为轻量程序。

不要在使用本 Skill 时修改产品定义或对象契约；它们是行为依据，不是附带修改授权。
